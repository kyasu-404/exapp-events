# exapp-events — Мероприятия

Nextcloud ExApp для синхронизации мероприятий из XLSX во внутренний и отдельный публичный Calendar, с email-напоминаниями на адреса из Excel. Проект — `exapp-events`, App ID — `exapp_events`, имя в Nextcloud — **Мероприятия**.

Приложение развёрнуто на Nextcloud 34 через существующий HaRP Proxy (Docker), AppAPI 34. Доступ администраторам: **Мероприятия** в меню Nextcloud. Nextcloud, HaRP и другие ExApp при установке не перезапускались. Эксплуатация и результаты проверки: [docs/deployment.md](docs/deployment.md). Первичное обследование: [docs/server-assessment.md](docs/server-assessment.md), полная матрица приёмки: [docs/acceptance.md](docs/acceptance.md).

## Возможности

- Административный интерфейс на Vue 3, TypeScript и `@nextcloud/vue`: обзор, источник, поля Excel, календари, уведомления, журнал.
- Рекурсивное чтение XLSX через Files API, привязка источника к стабильному ID, маски включения/исключения, debounce файловых событий и полная сверка.
- Определение года по ближайшей родительской папке, даты по листу; произвольный порядок колонок, настройка заголовков и предварительный просмотр.
- Идемпотентная CalDAV-синхронизация с постоянными UID, условными записями по ETag и восстановлением ручных изменений в календаре.
- Публикация выбранных строк в отдельный календарь без ответственного, email и внутренних метаданных; помощник iframe для штатной публичной ссылки Calendar.
- Постоянная очередь SMTP, интервалы напоминания, повтор после ошибок, письма об изменении/отмене для уже уведомлённых получателей.
- Dry-run с перечнем операций, защита массового удаления, подтверждение только актуального плана, диагностика и выгрузка журнала.
- SQLite с миграциями и восстановлением после перезапуска. Исходные XLSX приложение не изменяет.

## Локальная сборка и проверки

Нужны Python 3.12+, Node.js 22 и pnpm 11.19.0. Зависимости frontend зафиксированы в `pnpm-lock.yaml`, основные зависимости Python — в `pyproject.toml`.

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e '.[dev]'
corepack enable
corepack prepare pnpm@11.19.0 --activate
pnpm install --frozen-lockfile
.venv\Scripts\python.exe -m ruff check ex_app/lib tests scripts
.venv\Scripts\python.exe -m pytest -q
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

Если Corepack отсутствует, установите pnpm через `npm install --global pnpm@11.19.0`. На Linux вместо `.venv\Scripts\python.exe` используйте `.venv/bin/python`. Сборка создаёт `ex_app/js/events-main.js` и `ex_app/css/events-main.css`; генерируемые файлы не коммитятся.

Для просмотра UI без подключения к Nextcloud после сборки:

```powershell
.venv\Scripts\python.exe -m tests.ui_preview
```

Откройте `http://127.0.0.1:23101`. Это отдельный стенд с фиктивными API-ответами: он показывает интерфейс и формы, не реализует настоящую синхронизацию, файловый выбор Nextcloud и доставку писем. Остановите его `Ctrl+C`. [Снимок интерфейса](docs/ui-overview.png) сделан на этом стенде.

## Контейнер и подготовка метаданных

```sh
docker buildx build --platform linux/amd64 --load -t exapp-events:0.1.3 .
```

Dockerfile собирает frontend, устанавливает backend, проверяет checksum FRP 0.61.1 и поддерживает `amd64`/`arm64`. Приложение работает от UID 10001; стартовый процесс подготавливает права persistent volume и приватную копию сертификатов HaRP, затем понижает привилегии. Оригинальные сертификаты хоста не меняются. В HaRP-режиме FastAPI слушает Unix socket, FRP подключается к уже существующему прокси. Дополнительный публичный порт приложения не нужен.

`appinfo/info.xml` содержит **шаблон** образа `docker.io/exapp-events:0.1.3`. Перед установкой подготовьте метаданные с принадлежащим вам registry/namespace:

```sh
python scripts/prepare_release.py --registry ghcr.io --image YOUR_NAMESPACE/exapp-events --tag 0.1.3 --output dist/info.xml
```

Используйте namespace в нижнем регистре вместо `YOUR_NAMESPACE`. Скрипт только создаёт локальный XML; ничего не публикует и не устанавливает. Для закрытого registry сначала настройте доступ daemon к нему. На действующем сервере используется локальный образ `events.local/kyasu-404/exapp-events:0.1.3` и отдельное сопоставление `events.local → local` в существующем daemon: публичная публикация образа не требуется. Остальные registry mappings не заменялись.

## Последующая установка через существующий HaRP

Для установки на другом сервере используйте эти шаги. Действующее развёртывание описано в [docs/deployment.md](docs/deployment.md). Не нужно создавать второй HaRP или изменять `/opt/nextcloud/docker-compose.yml`.

1. В отдельном тестовом Nextcloud включите AppAPI, Calendar и Webhook Listeners; обеспечьте фоновые задания Nextcloud. Files-событие приходит после фактического сохранения файла, а не на каждом нажатии в ONLYOFFICE.
2. Проверьте выбранный registry, образ и содержимое `dist/info.xml`.
3. Разместите XML по URL, доступному Nextcloud, или по абсолютному пути **внутри контейнера Nextcloud**.
4. Зарегистрируйте приложение на существующем daemon. Синтаксис команды проверен через `occ --help` установленного AppAPI 34:

```sh
docker exec --user www-data nextcloud php occ app_api:app:register \
  exapp_events harp_proxy_docker --info-xml=HTTPS_URL_TO_INFO_XML --wait-finish
```

`HTTPS_URL_TO_INFO_XML` заменяется адресом подготовленного XML. Имя контейнера/daemon зависит от окружения; на действующем сервере это `nextcloud` и `harp_proxy_docker`, регистрация выполнена с локальным XML внутри Nextcloud. Не используйте `compose.dev.yml` для production: это только стенд прямого подключения к отдельному локальному тестовому Nextcloud.

AppAPI выдаёт `APP_ID`, `APP_SECRET`, `APP_DISPLAY_NAME`, `APP_VERSION`, `APP_HOST`, `APP_PORT`, `NEXTCLOUD_URL`, `APP_PERSISTENT_STORAGE`, а HaRP — `HP_SHARED_KEY`, `HP_FRP_ADDRESS`, `HP_FRP_PORT` и клиентские сертификаты. Не записывайте секреты в репозиторий. SDK сам выбирает Unix socket при наличии `HP_SHARED_KEY`.

## Первая настройка

1. Администратор открывает **Мероприятия** из меню Nextcloud.
2. В «Источник данных» выбирает пользователя и папку через штатный Files picker, включает рекурсивный обход и сохраняет настройки. Picker показывает дерево текущего администратора; доступ выбранного пользователя к папке проверяет backend.
3. В «Поля Excel» задаёт семь названий колонок и продолжительность по умолчанию, сохраняет и проверяет существующий XLSX.
4. В «Календари» выбирает владельца и отдельный внутренний календарь либо создаёт новый. Доступ сотрудников на чтение задаётся штатно в Nextcloud Calendar.
5. При необходимости выбирает другой публичный календарь, включает публикацию, вручную создаёт его публичную ссылку в Calendar и вставляет ссылку в помощник iframe.
6. В «Уведомления» выбирает SMTP Nextcloud или отдельный SMTP. На действующем сервере SMTP Nextcloud уже выбран и проверен. Для отдельного SMTP вводит параметры/пароль. Тестовое письмо отправляет на контролируемый адрес.
7. Выполняет «Проверить конфигурацию», затем «Проверить без изменений». После просмотра плана запускает настоящую синхронизацию.

После появления состояния источника замена владельцев, корневого ID или выбранных календарей требует отдельной миграции: API отклоняет такую замену, чтобы не оставить события в старом календаре. Впервые подключить публичный календарь позднее можно. Публикацию можно отключать и включать, сохраняя выбранный календарь. Перемещение/переименование самой папки с прежним ID отслеживается автоматически.

## Формат Excel

Пример структуры: `Мероприятия/2027/Сентябрь/План.xlsx`, лист `21.09` или `21.09.`. Ближайший родительский каталог `1900`–`2099` определяет год. Проверка русского названия месяца включена по умолчанию. Часовой пояс по умолчанию — `Europe/Moscow`.

| Аудитория | Время | Мероприятие | Ответственный | Email для уведомления | Напомнить за | На сайт |
| --- | --- | --- | --- | --- | --- | --- |
| 9 кабинет | 15:30 | Совещание | Иванова И.И. | school@example.org | 24ч;2ч | Да |
| 10 кабинет | 16:00–17:30 | Семинар | Петров П.П. | | | Нет |

Строка заголовков ищется в первых 50 строках; порядок колонок произвольный. Первые четыре колонки обязательны для события; отсутствие колонок уведомления/публикации выдаёт предупреждение. Строки, в которых указана только аудитория, разрешены: приложение пропускает их без предупреждений. Если заполнены другие поля, но обязательные значения отсутствуют, строка считается неполным мероприятием. Формулы без сохранённых значений не считаются свободной строкой с аудиторией. Разделители адресов — `;`, `,`, перенос строки. Повторяющиеся адреса/интервалы удаляются. Некорректный email не блокирует Calendar. Ответственный — обычный текст: приложение не ищет аккаунт/email по ФИО и не создаёт Calendar attendees.

Поддерживаются время Excel и строки `15:30`, `15.30`, диапазоны с дефисом или тире. Без окончания применяется настроенная продолжительность. Формулы читаются только по сохранённым cached values: приложение не вычисляет их. Дубликаты «файл + дата + время + нормализованное место» не объединяются, а отмечаются конфликтом. Неверная дата, обязательная ячейка или повреждённый XLSX запрещают удаление прежних событий этого файла до исправления.

## Сверка и удаление

Файловые webhook-события ставят задачу в постоянную очередь с debounce; задача запускает сверку дерева. Полная сверка по расписанию (по умолчанию 30 минут) страхует пропущенные события. Неудачная сверка повторяется через минуту, даже при выключенном регулярном расписании.

UID сохраняется при изменении названия/ответственного и перестановке строк. Изменение даты/времени/места меняет ключ: старое событие удаляется, новое создаётся. Связь для письма «изменено» определяется только при однозначном совпадении файла, названия и ответственного; неоднозначный случай обрабатывается как отмена/новое событие.

При удалении строки сохраняется прошедшая история; при исчезновении файла действуют политики «будущие» (по умолчанию), «все» или «сохранить». Недоступная корневая папка, ошибки обхода, неустойчивый ETag и повреждённые файлы не превращаются в пустой источник. Чужие события без служебных признаков приложение не удаляет.

Защита по умолчанию останавливает изменения **календарей** при удалении более 50 событий либо более 25% событий отдельного файла/целевого календаря при минимуме 20 удалений. Проверенные строки Excel и очередь писем обновляются независимо: ожидание подтверждения не задерживает напоминания, исчезнувшие строки отменяют старые задания. UI показывает операции и предлагает подтвердить или отменить изменения календарей. При подтверждении источник и CalDAV перечитываются; изменившийся план требует нового просмотра. Dry-run записывает только отчёт сверки, не меняет состояние источников/очередь, не записывает Calendar и не отправляет письма.

Для полной автоматической синхронизации отключите «Запрашивать подтверждение при массовом удалении» в разделе «Источник данных». Настройка сохраняется после обновления/перезапуска; её изменение автоматически ставит сверку в очередь. Недоступная корневая папка и некорректные XLSX сохраняют прежние проверки и защиту событий.

В том же разделе можно задать архивную папку в файлах владельца источника, вручную или через выбор папки. Пустое поле отключает исключение. Архив может находиться внутри источника или отдельно, но не может совпадать с источником или содержать его. Папка отслеживается по ID, включая переименование. Её вложенные папки и XLSX не обходятся и не читаются; предварительная проверка архивного XLSX также отклоняется. Для ранее отслеживаемых файлов проверяются только ID и текущий путь. Перенос в архив удаляет все связанные события из обоих календарей, включая прошедшие, независимо от политики обычного исчезновения файла; ожидающие напоминания отменяются. При возврате XLSX в источник синхронизация возобновляется.

Внутренний календарь, публичный календарь и SMTP независимы: недоступность публичного календаря не блокирует внутренний и очередь напоминаний. После частичной ошибки следующий проход сравнит реальное состояние Calendar и повторит только недостающие операции. Числа операций в отчёте показывают план; фактические успешные операции и ошибки есть в журнале.

## SMTP и перезапуск

В режиме **SMTP Nextcloud** отдельный модуль `exapp_events_bridge` в persistent `custom_apps` принимает только подписанные AppAPI-запросы `exapp_events` и отправляет через публичный `OCP\Mail\IMailer`. Пароль SMTP остаётся в Nextcloud; изменения его настройки применяются к следующим отправкам. Модуль устанавливается из `nextcloud_bridge/exapp_events_bridge` и включается `occ app:enable exapp_events_bridge` без перезапуска облака. Диагностика выполняет SMTP/TLS/AUTH/QUIT без доставки письма.

После установки или обновления SMTP-модуля каталог и его файлы должны принадлежать пользователю web-сервера Nextcloud. Для текущего Docker-контейнера: `docker exec --user root nextcloud chown -R www-data:www-data /var/www/html/custom_apps/exapp_events_bridge`. Это устраняет предупреждение Nextcloud о владельце каталога приложения; перезапуск не требуется.

Приложение читает сохранённый XLSX из Files. При редактировании в ONLYOFFICE сохранение изменений внутри активной сессии и передача обновлённого XLSX в Nextcloud выполняются отдельно. На текущем сервере автоматическая передача включена с интервалом **10 минут**, проверка таймеров выполняется раз в минуту. Настройка хранится в постоянном volume ONLYOFFICE `Data/runtime.json`; образец — [onlyoffice-auto-save.json](docs/onlyoffice-auto-save.json). Конфигурация общая для ONLYOFFICE и не добавляет прямую интеграцию редактора в ExApp. См. [сохранение файлов в ONLYOFFICE](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/saving-file). Время отправки рассчитывается как начало события минус «Напомнить за»; при планировании учитывайте задержку передачи файла. Например, 07.10 в 16:00 и «24ч» означают отправку 06.10 в 16:00; при поступлении файла после этого времени и `overdue_minutes=0` задание будет пропущено.

В режиме **Отдельный SMTP** пароль хранится в sensitive AppConfig Nextcloud, не в SQLite и не возвращается в UI. Письма plain text + HTML; HTML-поля экранируются. Очередь содержит получателя, UID, offset, ревизию и уникальный dedupe key. После успешной отправки повторная идентичная сверка не ставит то же письмо повторно.

После SMTP-ошибки выполняются до пяти попыток с паузами 1, 5, 15 и 60 минут. Просроченные напоминания после простоя пропускаются по умолчанию; окно допустимой просрочки настраивается. Начавшееся мероприятие больше не получает напоминаний. Изменения отменяют старые pending/retry задания; отмена будущего события уведомляет только ранее уведомлённые адреса.

Если время отправки прошло до постановки в очередь, задание сохраняется со статусом `skipped` и причиной. Обзор показывает ожидающие, отправленные, пропущенные и ошибочные письма, а также последние 20 заданий. Отмена плана календарей не отменяет уже обработанные напоминания из сохранённого Excel.

SMTP не даёт гарантии ровно одной доставки: при обрыве после принятия письма сервером результат может быть неизвестен. Задание, прерванное в состоянии `sending`, становится `failed` и не повторяется автоматически. Перед «Повторить ошибки» проверьте доставку; ручной повтор может отправить письмо повторно. Для прямого SMTP Message-ID детерминирован; в режиме SMTP Nextcloud его формирует штатный Mailer. Ни один из вариантов не даёт гарантии дедупликации на стороне получателя.

## Хранилище, обновление и диагностика

SQLite `events.sqlite3` и её WAL находятся в `APP_PERSISTENT_STORAGE`, который монтирует AppAPI. Docker `VOLUME /data` относится к локальному значению по умолчанию; фактический путь AppAPI может отличаться. Не удаляйте управляемый том при обновлении. Миграции выполняются транзакционно, прерванные сверки помечаются и повторяются при восстановлении.

Перед обновлением отключите ExApp, сделайте согласованную резервную копию всего persistent volume и конфигурации Nextcloud (sensitive AppConfig нужен для восстановления SMTP-пароля), подготовьте новый образ и метаданные. Обновляйте через штатный AppAPI, затем включите, выполните диагностику и dry-run. При откате версии с другой схемой SQLite восстанавливайте согласованную копию тома; автоматического downgrade миграций нет.

Журнал фильтруется по уровню, подсистеме, файлу и диапазону дат; выгружается в CSV и хранится 30/90/180/365 дней. Диагностика проверяет AppAPI, наличие четырёх файловых listeners, запись в storage, SQLite, доступ к папке, CalDAV и SMTP-соединение без отправки письма.

Неизменившиеся проблемы источника записываются в журнал один раз, затем снова только после исправления и повторного появления. История сохраняется; счётчик на обзоре показывает текущие проблемы последней сверки. В предупреждениях о неполной строке указаны отсутствующие поля, лист и номер строки.

Управление защищено на двух уровнях: маршруты AppAPI `ADMIN` и проверка группы `admin` backend. Heartbeat доступен без пользовательской сессии, lifecycle и файловые callbacks требуют доверенную подпись AppAPI. Поддельная подпись отклоняется до SDK, чтобы его диагностические сообщения не раскрыли секрет. Callback не опубликован как публичный proxy route.

Если обе копии связи публичного события с источником потеряны — SQLite и внутренние метаданные Calendar — приложение сохраняет неизвестное публичное событие и пишет предупреждение для ручной проверки. Восстановление из Calendar не заменяет резервную копию очереди SMTP.

## Структура

```text
appinfo/info.xml                 AppAPI, образ, права маршрутов
ex_app/lib/main.py               административный API и lifecycle
ex_app/lib/runtime.py            фоновые задачи и включение/отключение
ex_app/lib/db/                   SQLite и миграции
ex_app/lib/services/             Files, Excel, CalDAV, sync, SMTP, reminders
ex_app/src/                     Vue / TypeScript UI
scripts/                        HaRP/FRP, healthcheck, release metadata
nextcloud_bridge/               отдельный SMTP-модуль Nextcloud
tests/                          backend и изолированный визуальный стенд
docs/                           обследование и приёмка
Dockerfile                      автономная сборка образа
.github/workflows/ci.yml         проверки и сборка контейнера без публикации
```

Исходное ТЗ: [docs/specification.md](docs/specification.md). Использован официальный [Python ExApp skeleton](https://github.com/nextcloud/app-skeleton-python), APIs сверены с установленным AppAPI и SDK 0.30.3. CalDAV использует RFC 4791/4918 через изолированный адаптер authenticated transport SDK. Лицензия проекта: AGPL-3.0-or-later.
